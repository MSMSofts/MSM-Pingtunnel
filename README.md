# Pingtunnel Manager 3.0 — Pairing v3

مدیریت بسیار سبک برای یک تونل **ICMP** بین فقط **دو VPS: ایران و خارج**. هستهٔ انتقال داده همچنان **Go (esrrhs/pingtunnel)** است؛ Rust صرفاً ابزار منو، تولید/ذخیره کلید و مدیریت systemd است. HA، سرور اضافه و Failover وجود ندارند.

## راه‌اندازی یکپارچه؛ فقط پنج سؤال روی هر VPS

یک فرمان برای نصب یا به‌روزرسانی روی Debian/Ubuntu با پردازنده AMD64 یا ARM64:

```bash
curl -fsSL https://raw.githubusercontent.com/meysamrn/Pingtunnel_manager/main/Source/install.sh -o /tmp/pingtunnel-install.sh && sudo bash /tmp/pingtunnel-install.sh
```

سپس دستور `pingtunnel` یا `sudo pingtunnel setup` را اجرا کن.

هر دو VPS دقیقاً همین پنج مرحله را دارند:

1. **این VPS کجاست؟** ایران یا خارج (هویت ثابت؛ نه جهت ICMP).
2. **IP سرور مقابل؟** آدرس IPv4 که واقعاً برای ترافیک ICMP از آن استفاده می‌شود. در سمت خارج ورود این مقدار، مبدأ مجاز ICMP را محدود می‌کند.
3. **کلید جفت‌سازی؟** هنگام اولین Setup در خارج، یک کلید تصادفی ۳۲ بایتی تولید و فقط برای انتقال امن به VPS ایران نمایش داده می‌شود؛ ایران همان کلید را به‌صورت مخفی وارد می‌کند. در Setupهای بعدی همان کلید محفوظ می‌ماند؛ برای نمایش دوباره `sudo pingtunnel key` را اجرا کن.
4. **ترافیک داخل تونل؟** TCP یا UDP. هر دو VPS باید یک پروتکل را انتخاب کنند؛ حامل بین دو VPS همچنان ICMP است.
5. **پورت همین VPS؟** در ایران پورت دریافت VPN کاربران؛ در خارج پورت سرویس VPN محلی (مثلاً s-ui/Hysteria 2). پورت‌ها مستقل‌اند. مقادیر پیشنهادی TCP=443 و UDP=444 هستند؛ تغییر آن‌ها آزاد است.

پس از تأیید پاسخ‌ها، فایل `/opt/pingtunnel/conf/config.json` با مجوز `0600` نوشته می‌شود و واحد systemd اجرا می‌شود. تنظیمات دیگر از جمله رمزنگاری، کنترل ازدحام BB، Adaptive Performance، restart و شروع خودکار توسط نرم‌افزار مدیریت می‌شود. منوی Easy/Advanced و تنظیم دستی الگوریتم حذف شده‌اند.

## مثال واقعی Hysteria 2

- سمت ایران: ایران / IP خارج / کلید مشترک / UDP / **444**
- سمت خارج: خارج / IP ایران / همان کلید / UDP / **8443**
- Hysteria 2 در s-ui روی خارج `127.0.0.1:8443/UDP` گوش می‌دهد و کلاینت VPN فقط `IRAN_IP:444` را می‌شناسد.

```text
Hysteria 2 client --UDP:444--> Iran [Go client]
                          --encrypted ICMP-->
Foreign [Go server] --UDP:8443--> s-ui/Hysteria 2 on 127.0.0.1
```

این نسخه به‌صورت اجباری و سمت **خارج**، مقصد `127.0.0.1:PORT` را تعیین می‌کند. مقدار `target` ارسالی از ایران، حتی برای UDP، روی Go server بازنویسی می‌شود. سرور خارج تنها ICMP رمزگشایی‌شده با کلید مشترک و IP مبدأ مجاز ایران را پردازش می‌کند؛ UDP/TCP نامتجانس رد می‌شوند. این رفتار با VPNهای مبتنی بر TCP یا UDP سازگار است؛ اما هر اجرای این تونل یک حالت TCP یا UDP دارد، نه دو ورودی هم‌زمان.

## کلید رمزنگاری مستقل از نقش

کلید **Pairing Root** یک مقدار تصادفی ۲۵۶ بیتی است که در `/dev/urandom` ساخته می‌شود؛ کلید وابسته به Client/Server نیست، پس آماده نگهداری در معماری تغییر مسیر ICMP در آینده است. از همین ریشه، شناسه عددی ۳۱ بیتی Go با SHA-256 مشتق می‌شود؛ از کاربر پسورد عددی پرسیده نمی‌شود. Go از HKDF-SHA256 برای ساخت **کلیدهای جداگانه AES-256-GCM و XChaCha20-Poly1305 در هر جهت فیزیکی ایران→خارج و خارج→ایران** استفاده می‌کند. AES/XChaCha خودکار پس از بنچمارک شروع Go انتخاب می‌شود؛ هر دو سمت هر دو را رمزگشایی می‌کنند و شناسه الگوریتم در برچسب احراز اصالت رمزنگاری محافظت می‌شود.

کلید رمزنگاری هیچ‌وقت به‌عنوان آرگومان قابل مشاهده فرایند Go وارد نمی‌شود؛ Go تنظیمات را از فایل `/run/pingtunnel-core.json` با دسترسی `0600` می‌خواند. هیچ حالت plaintext و هیچ کلید جایگزین ضعیفی در پیکربندی v3 معتبر نیست.

**محدودیت صادقانه:** خود الگوریتم رمزنگاری به‌تنهایی باعث پنهان‌شدن ICMP از شناسایی شبکه نمی‌شود. Anti-Replay Window مستقل و Forward Secrecy با توافق کلید موقت هنوز پیاده‌سازی نشده‌اند. معماری فعلاً **Direct: ایران → خارج** است؛ تغییر خودکار Direct/Reverse و Reverse Forwarding هنوز ساخته نشده و تغییر جهت در آینده به توسعه Go نیاز دارد. اما با آن تغییر کلید جفت‌سازی نباید تعویض شود.

## Adaptive Performance

Go Client ایران از Pingهای معمول خودش RTT، Jitter و پاسخ‌ندادن را نمونه‌برداری می‌کند؛ پارامترهای شروع نشست‌های TCP جدید را بدون قطع نشست جاری انتخاب می‌کند. کنترل ازدحام BB اصلی Go برای نشست‌های برقرار فعال است. فرمان `sudo pingtunnel performance` یا گزینه 8 منو گزارش را نشان می‌دهد. این قابلیت کنترل پهنای‌باند UDP یا تغییر زنده پنجره نشست‌های جاری نیست.

## ناسازگاری عمدی با نسخه‌های قبل از 3.0

**سازگاری و مهاجرت از تنظیمات پیشین عمداً حذف شده است.** قالب جدید `schema_version=3` اجباری است. اگر فایل قدیمی وجود داشته باشد، نصب‌کننده **قبل از دست‌زدن به سرویس جاری خطا می‌دهد**؛ آن فایل را در محل امن پشتیبان بگیر، سپس با تصمیم خودت منتقل/حذف کن و v3 را به‌طور مستقل روی **هر دو VPS** راه‌اندازی کن. هیچ کلید قدیمی، نقش Client/Server قدیمی یا هدف مسیریابی قدیمی خودکار وارد قالب جدید نمی‌شود. از این نسخه به بعد، حفظ سازگاری با قالب v3 مبنای توسعه‌های بعدی است.

تغییر پورت یا پروتکل خارج باید با سرویس واقعی s-ui هماهنگ شود؛ اگر s-ui روی `127.0.0.1` فقط گوش نمی‌دهد یا فایروال مانع است، ارتباط برقرار نمی‌شود. همچنین صحت عبور ICMP و کیفیت عملکرد باید روی دو VPS واقعی سنجیده شود.
