# Pingtunnel Manager 3.2 — Security hardening, Pairing v3, Wire v4

مدیریت بسیار سبک برای یک تونل **ICMP** بین فقط **دو VPS: ایران و خارج**. هستهٔ انتقال داده همچنان **Go (esrrhs/pingtunnel)** است؛ Rust صرفاً ابزار منو، تولید/ذخیره کلید و مدیریت systemd است. HA، سرور اضافه و Failover وجود ندارند.

## راه‌اندازی یکپارچه؛ فقط پنج سؤال روی هر VPS

یک فرمان برای نصب یا به‌روزرسانی روی Debian/Ubuntu با پردازنده AMD64 یا ARM64:

```bash
curl -fsSL https://raw.githubusercontent.com/meysamrn/Pingtunnel_manager/main/Source/install.sh -o /tmp/pingtunnel-install.sh && sudo bash /tmp/pingtunnel-install.sh
```

سپس دستور `pingtunnel` یا `sudo pingtunnel setup` را اجرا کن.

هر دو VPS دقیقاً همین پنج مرحله را دارند:

1. **این VPS کجاست؟** ایران یا خارج (هویت ثابت؛ نه جهت ICMP).
2. **IP سرور مقابل؟** آدرس IPv4 که واقعاً برای ترافیک ICMP از آن استفاده می‌شود. در سمت خارج ورود این مقدار، مبدأ مجاز ICMP را محدود می‌کند.
3. **کلید جفت‌سازی؟** هنگام اولین Setup در خارج، یک کلید تصادفی ۳۲ بایتی تولید و فقط برای انتقال امن به VPS ایران نمایش داده می‌شود؛ ایران همان کلید را به‌صورت مخفی وارد می‌کند. در Setupهای بعدی همان کلید محفوظ می‌ماند؛ برای نمایش دوباره `sudo pingtunnel key` را اجرا کن.
4. **ترافیک داخل تونل؟** TCP یا UDP. هر دو VPS باید یک پروتکل را انتخاب کنند؛ حامل بین دو VPS همچنان ICMP است.
5. **پورت همین VPS؟** در ایران پورت دریافت VPN کاربران؛ در خارج پورت سرویس VPN محلی (مثلاً s-ui/Hysteria 2). پورت‌ها مستقل‌اند. مقادیر پیشنهادی TCP=443 و UDP=444 هستند؛ تغییر آن‌ها آزاد است.

پس از تأیید پاسخ‌ها، فایل `/opt/pingtunnel/conf/config.json` با مجوز `0600` نوشته می‌شود و واحد systemd اجرا می‌شود. تنظیمات دیگر از جمله رمزنگاری، کنترل ازدحام BB، Adaptive Performance، restart و شروع خودکار توسط نرم‌افزار مدیریت می‌شود. منوی Easy/Advanced و تنظیم دستی الگوریتم حذف شده‌اند.

## مثال واقعی Hysteria 2

- سمت ایران: ایران / IP خارج / کلید مشترک / UDP / **444**
- سمت خارج: خارج / IP ایران / همان کلید / UDP / **8443**
- Hysteria 2 در s-ui روی خارج `127.0.0.1:8443/UDP` گوش می‌دهد و کلاینت VPN فقط `IRAN_IP:444` را می‌شناسد.

```text
Hysteria 2 client --UDP:444--> Iran [Go client]
                          --encrypted ICMP-->
Foreign [Go server] --UDP:8443--> s-ui/Hysteria 2 on 127.0.0.1
```

این نسخه به‌صورت اجباری و سمت **خارج**، مقصد `127.0.0.1:PORT` را تعیین می‌کند. مقدار `target` ارسالی از ایران، حتی برای UDP، روی Go server بازنویسی می‌شود. سرور خارج تنها ICMP رمزگشایی‌شده با کلید مشترک و IP مبدأ مجاز ایران را پردازش می‌کند؛ UDP/TCP نامتجانس رد می‌شوند. این رفتار با VPNهای مبتنی بر TCP یا UDP سازگار است؛ اما هر اجرای این تونل یک حالت TCP یا UDP دارد، نه دو ورودی هم‌زمان.

## کلید رمزنگاری مستقل از نقش

کلید **Pairing Root** یک مقدار تصادفی ۲۵۶ بیتی است که در `/dev/urandom` ساخته می‌شود؛ کلید وابسته به Client/Server نیست، پس آماده نگهداری در معماری تغییر مسیر ICMP در آینده است. از همین ریشه، شناسه عددی ۳۱ بیتی Go با SHA-256 مشتق می‌شود؛ از کاربر پسورد عددی پرسیده نمی‌شود. Go از HKDF-SHA256 برای ساخت **کلیدهای جداگانه AES-256-GCM و XChaCha20-Poly1305 در هر جهت فیزیکی ایران→خارج و خارج→ایران** استفاده می‌کند. AES/XChaCha خودکار پس از بنچمارک شروع Go انتخاب می‌شود؛ هر دو سمت هر دو را رمزگشایی می‌کنند و شناسه الگوریتم در برچسب احراز اصالت رمزنگاری محافظت می‌شود.

کلید رمزنگاری هیچ‌وقت به‌عنوان آرگومان قابل مشاهده فرایند Go وارد نمی‌شود؛ Go تنظیمات را از فایل `/run/pingtunnel-core.json` با دسترسی `0600` می‌خواند. هیچ حالت plaintext و هیچ کلید جایگزین ضعیفی در پیکربندی v3 معتبر نیست.

**لایه امنیت v4 (از نسخه 3.1):** پیش از ارسال هر داده، ایران و خارج طی یک تبادل چهارپیامیِ **X25519 موقت** روی خود ICMP توافق کلید می‌کنند. پیام‌های اولیه با کلید جفت‌سازی احراز اصالت می‌شوند و پیام‌های پایانی با کلید حاصل از توافق X25519 تأیید می‌شوند. کلیدهای داده برای هر نشست از X25519 و کلید جفت‌سازی به‌صورت HKDF مشتق می‌شوند؛ کلیدهای AES-256-GCM یا XChaCha20-Poly1305 همچنان بر اساس بنچمارک انتخاب می‌شوند. این طراحی **Forward Secrecy در سطح نشست** فراهم می‌کند؛ افشای بعدی کلید مشترک به‌تنهایی برای رمزگشایی نشست‌های ضبط‌شده کافی نیست، مادامی که کلیدهای موقت و حافظه نشست افشا نشده باشند.

**Independent Anti-Replay:** داده‌ها در فریم نسخه‌دار جدید با شناسه نشست، شماره توالی ۶۴ بیتی و تگ احراز اصالت فرستاده می‌شوند. Go تنها بعد از تایید تگ اجازه مصرف شماره توالی را می‌دهد. پنجره ۱۰۲۴ بسته، ترتیب نامنظم مشروع را می‌پذیرد اما تکرار و بسته قدیمی را رد می‌کند. بسته‌های قدیمی `PTA1` پذیرفته نمی‌شوند؛ پایین‌آوردن خودکار امنیت به پروتکل قدیم وجود ندارد.

**Smart Recovery:** در صورت قطع طولانی ارتباط در حالی که استفاده واقعی از تونل وجود دارد، کلاینت Go پس از یک دوره ۳۵ ثانیه‌ای سکوت معتبر، یک نشست X25519 تازه برقرار می‌کند. تلاش‌ها با تأخیر افزایشی محدود (حداکثر ۸ ثانیه) و همان ICMP Ping موجود انجام می‌شود؛ هیچ VPS سوم، Failover، نظارت دائمی Rust یا Restart متوالی systemd وجود ندارد. اتصال‌های TCP/UDP فعال پس از قطع طولانی ممکن است برای بازیابی کامل به اتصال مجدد اپلیکیشن VPN احتیاج داشته باشند. Smart Recovery با ایجاد مجدد نشست، همهٔ جریان‌های قطع‌شده را معجزه‌آسا ادامه نمی‌دهد.

**سازگاری نسخه‌ها:** قالب تنظیمات `schema_version=3` و کلید جفت‌سازی از 3.0 تا 3.2 ثابت‌اند. نسخه 3.2 با پروتکل امن سیمی `PTH4/PTD4` نسخه 3.1 سازگار است، هرچند هنگام راه‌اندازی مجدد سرویس‌ها ممکن است نشست‌ها قطع شوند و نیاز به اتصال مجدد داشته باشند. نسخه 3.0 از قالب سیمی قدیمی `PTA1` استفاده می‌کند و با 3.1/3.2 به‌صورت هم‌زمان کار نمی‌کند؛ پایین‌آوردن خودکار امنیت وجود ندارد. قبل از ارتقای نسخه‌های سیمی ناسازگار، هر دو VPS باید در بازه نگهداری به‌روزرسانی شوند.

**محدودیت:** خود رمزنگاری ICMP را از دید شبکه پنهان نمی‌کند. حفاظت در برابر DoS حجمی در سطح ICMP تضمین نشده است. تونل معکوس/تعویض Direct و Reverse هنوز پیاده‌سازی نشده و همچنان معماری فقط **Direct: ایران → خارج** است. کلید جفت‌سازی در توسعه Reverse آینده ثابت می‌ماند.


## اصلاحات امنیت و پایداری 3.2

- **Anti-Replay کنترل نشست:** پیام آغاز مذاکره قدیمی، حتی با MAC معتبر ضبط‌شده، نشست دادهٔ فعال را قطع نمی‌کند. درخواست جدید به‌عنوان *handshake candidate* جداگانه آماده و فقط پس از اثبات کلید موقت X25519 جایگزین می‌شود. ClientHello تکراری شناخته‌شده رد می‌شود و تعداد handshakeهای همزمان محدود است. این سازوکار جلوی همهٔ حملات حجمی ICMP را نمی‌گیرد.
- **صف محدود Smart Recovery:** هنگام آماده‌نبودن نشست رمزنگاری، پیام‌های DATA تا سقف ۲۵۶ بسته، ۲ مگابایت و حداکثر ۱۲ ثانیه نگهداری می‌شوند. بعد از احراز هویت دوطرفه، بسته‌های باقی‌مانده با کلید جدید رمزگذاری می‌شوند. تعداد بسته‌های دورریخته‌شده در صورت پایان مهلت/پرشدن صف گزارش می‌شود؛ تداوم بی‌نقص نشست‌های TCP/UDP پس از قطعی طولانی تضمین نیست.
- **خروج خطای واقعی:** خطای تنظیمات یا شروع Go با کد غیرصفر پایان می‌یابد و `systemd` می‌تواند طبق `Restart=on-failure` واکنش نشان دهد.
- **گزارش عملیاتی:** با `sudo pingtunnel security` یا گزینه ۱۳ منو، وضعیت مذاکره، شماره نسخه سیمی، زمان آخرین پیام معتبر، تعداد رد بازپخش، خطاهای احراز اصالت، بازیابی و صف بسته‌ها دیده می‌شود. فایل وضعیت خصوصی `/run/pingtunnel-security.json` شامل کلید نیست؛ گزارش قدیمی هشدار داده می‌شود.
- **انتشار نسخه‌بندی‌شده:** نصب‌کننده از Release ثابت `v3.2.0` و Manifest دارای SHA256 هر دو باینری استفاده می‌کند؛ علاوه بر آن هسته Go باید شناسه `config-schema=3 wire=4` را اعلام کند. نسخهٔ rolling برای سازگاری با لینک‌های قبلی همچنان به‌روز می‌شود. اسکریپت Python قدیمی از مخزن حذف شده است.

```bash
sudo pingtunnel security
sudo pingtunnel performance
sudo pingtunnel status
```

**تست‌ها:** تست‌های کنترل نشست، ضدبازپخش، داده‌های صف‌شده، قطع/وصل توافق کلید، Race Detector و خروج خطای CLI در CI اجرا می‌شوند. تست واقعی پایداری ICMP و Hysteria 2 روی دو VPS هنوز لازم است؛ صحت رمزنگاری سفارشی بدون ممیزی مستقل تضمین نشده است.

## Adaptive Performance

Go Client ایران از Pingهای معمول خودش RTT، Jitter و پاسخ‌ندادن را نمونه‌برداری می‌کند؛ پارامترهای شروع نشست‌های TCP جدید را بدون قطع نشست جاری انتخاب می‌کند. کنترل ازدحام BB اصلی Go برای نشست‌های برقرار فعال است. فرمان `sudo pingtunnel performance` یا گزینه 8 منو گزارش را نشان می‌دهد. این قابلیت کنترل پهنای‌باند UDP یا تغییر زنده پنجره نشست‌های جاری نیست.

## ناسازگاری عمدی با نسخه‌های قبل از 3.0

**سازگاری با قالب تنظیمات v3 از نسخه 3.0 به بعد حفظ می‌شود، اما تنظیمات قبل از 3.0 همچنان پشتیبانی نمی‌شوند.** قالب `schema_version=3` اجباری است. اگر فایل قدیمی وجود داشته باشد، نصب‌کننده **قبل از دست‌زدن به سرویس جاری خطا می‌دهد**؛ آن فایل را در محل امن پشتیبان بگیر، سپس با تصمیم خودت منتقل/حذف کن و v3 را به‌طور مستقل روی **هر دو VPS** راه‌اندازی کن. هیچ کلید قدیمی، نقش Client/Server قدیمی یا هدف مسیریابی قدیمی خودکار وارد قالب جدید نمی‌شود. از این نسخه به بعد، حفظ سازگاری با قالب v3 مبنای توسعه‌های بعدی است.

تغییر پورت یا پروتکل خارج باید با سرویس واقعی s-ui هماهنگ شود؛ اگر s-ui روی `127.0.0.1` فقط گوش نمی‌دهد یا فایروال مانع است، ارتباط برقرار نمی‌شود. همچنین صحت عبور ICMP و کیفیت عملکرد باید روی دو VPS واقعی سنجیده شود.
